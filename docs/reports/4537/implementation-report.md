# Implementation Report: a runtime requirement lands where the target runs it (#4537)

A real LLD run on a private target approved a plan whose requirements described runtime behaviour, while its file list changed only an offline compiler and added a module the target never runs. The target built the concept in one TypeScript function the plan never listed. One new module, `assemblyzero/workflows/requirements/runtime_homes.py`, now finds where such a concept is built. Three readers use the result.

A concept is a name the issue writes as an identifier that the target declares as a type. Its builders are the non-test functions whose declared return type names it. Parsers make every decision: `ast` reads Python and tree-sitter reads TypeScript. The one regular expression is a tokenizer that splits text into identifier-shaped words. The issue-side reading takes backticked words, camel-case words, and capitalized words that do not open a sentence or a table cell and do not label a number (`Section 6`). It skips headings and fenced blocks.

- R1: `analyze_codebase` (N0b) stores `runtime_homes` and prints each home, or prints that the issue names none. The drafter is shown the builder file as where the change lands, on the first draft and on every revision. The builder files also go first into the interface surface. The revision refresh now covers them too, so a draft that leaves them out still sees their signatures.
- R2: mechanical validation Step 6e, `validate_requirements_land_where_they_run`, refuses a Section 3 requirement that names a concept while Section 2.1 changes no file that builds or declares it. A declaring file counts, so a requirement about a concept the program consumes rather than builds is not refused. The refusal names the requirement number, quotes the requirement, and names the builder file to add as Modify.
- R3: the review node appends a brief to the LLD review instructions. The brief lists the draft's Section 2.1 files and asks after each requirement which listed file implements it. A requirement no listed file can implement is a Tier 1 BLOCKING finding. The reviewer also sees the homes section. `docs/skills/0702c-LLD-Review-Prompt.md` gains the matching Tier 1 Implementability check, as v2.8.0.

The new N0b halt, for a source file the finder cannot read or parse, joins the `lld.arc_unreadable` row in `assemblyzero/core/gate_registry.py`. The first version of Step 6e returned early when there were no homes, and the fail-open ratchet refused it. Every requirement is now read whatever the homes hold.
